Catching laundering by the company an account keeps

The IBM anti-money-laundering dataset is about 0.9% laundering. A gradient-boosted baseline copes by calling almost everything clean. Modeling the same transactions as a graph and passing messages along the money trail moves the needle on the metric that matters: how much laundering you actually catch.

Detection rate — recall on the held-out split

XGBoost baseline 2 of 1,033 laundering cases
0.19%
Graph Transformer 125 of 2,201 laundering nodes
5.7%

Not a controlled benchmark. The baseline scores individual transactions; the graph model scores account nodes on a later graph build with its own split. Read it as direction of travel — roughly a 30× jump in recall — not a like-for-like score.

The graph model gives up headline accuracy and precision — it raises far more false flags — to roughly triple its F1 and catch laundering the baseline never sees. On a problem this imbalanced, a 99.9%-accurate model that finds two cases in a thousand is the trap, not the target.

The baseline keys on bookkeeping artifacts — whether both accounts share a bank, when the transaction posted. The graph model is handed no such shortcuts: every node starts from the same constant feature, so anything it learns comes from the shape of the money flow itself.

Data — IBM Transactions for Anti-Money Laundering (HI-Small)
Graph — ~514K account nodes, ~4.1M transaction edges, 13 edge features
Model — 2× PyG TransformerConv with edge attributes, structure-only node inputs
